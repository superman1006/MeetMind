## 0. 阅读指南：编号与符号约定

> 如果你是第一次看产品文档，先读这一节。下面是本文里反复出现的几类"代号"分别代表什么、怎么读。

| 符号 | 英文 / 全称 | 中文含义 | 用来做什么 | 例子 |
|---|---|---|---|---|
| **P0 / P1 / P2** | Priority | **优先级** | 标记一条需求有多重要、多紧急。数字越小越重要：P0 = 必须做（不做产品就不能上线），P1 = 重要，P2 = 锦上添花、可延后。（本文目前只用到 P0~P2；有些团队还会用 P3 表示"想到了但暂不做"） | 「用户登录」是 **P0**；「会话分组」是 **P2** |
| **G1 / G2 / G3 …** | Goal | **业务目标** | 给"我们想达成什么"编号，方便后面引用。G = Goal。见第 3 章 | **G1** = 支持多用户安全使用 |
| **M1 / M2 … M8** | Module | **功能模块** | 把一堆相关需求打包成一个"模块"并编号，本文共 8 个模块。M = Module | **M1** = 用户与账户体系；**M5** = 工具治理与安全 |
| **FR** | Functional Requirement | **功能需求** | 表示"这是一条具体的功能要求"（与之相对的是"非功能需求"，如性能、安全） | 整个第 6 章都是 FR |
| **FR-M1-01** | FR-Module-Number | **一条需求的唯一编号** | 这是最常见的代号，读法是「**FR**（功能需求）-**M1**（属于第 1 个模块）-**01**（该模块下第 1 条）」。每条需求都有独一无二的编号，方便开发、测试、讨论时精确指代某一条 | **FR-M1-01** = 第 1 模块（用户体系）里的第 1 条需求 = "用户注册"；**FR-M5-03** = 第 5 模块里第 3 条 = "高风险操作沙箱" |
| **R1 / R2 / R3** | Release / Roadmap | **里程碑（发布批次）** | 把需求分批交付，每一批叫一个里程碑。R = Release。R1 先做、R2 次之、R3 最后。见第 9 章 | **R1** = 多用户可用 + 安全底座 |
| **NFR** | Non-Functional Requirement | **非功能需求** | 不是某个具体功能，而是对整体的质量要求（性能、安全、可维护性等） | 见第 7 章 |
| **OQ** | Open Question | **待澄清问题** | 还没拍板、需要进一步确认的点 | 见 11.4 |
| **TBD** | To Be Determined | **待定** | 这个信息还没确定，之后补 | 产品负责人：TBD |

**一句话记忆**：`P` 看**多重要**、`M` 看**属于哪个模块**、`FR-Mx-NN` 是**某条需求的身份证号**、`R` 看**第几批做**、`G` 是**目标**。

## 1. 文档说明

### 1.1 文档目的

本文档定义 MeetMind 从「一个可用的多 Agent 聊天 Demo」演进为「可面向多用户、可工程化落地的智能会议协作平台」所需的产品需求。文档同时承担三个作用：

1. **对齐现状**：明确当前已实现的能力基线（Section 5），避免重复建设。
2. **定义增量**：把待实现需求拆解为可独立交付的功能模块（Section 6），每条需求带验收标准与优先级。
3. **指导排期**：给出里程碑与路线图（Section 9），作为研发拆 Story、估时、验收的依据。

### 1.2 读者对象

产品经理、前后端研发、测试、架构师、项目管理。

### 1.3 优先级定义

| 优先级 | 含义 | 排期预期 |
|---|---|---|
| **P0** | 核心路径 / 多用户上线的前置必备能力，缺失则产品不可对外 | 必须在对应里程碑交付 |
| **P1** | 显著提升体验或可运维性的重要能力 | 尽量在对应里程碑交付 |
| **P2** | 增强型 / 锦上添花能力 | 资源允许时交付，可延后 |

### 1.4 术语表

| 术语 | 说明 |
|---|---|
| Agent | 系统中的角色智能体，目前有架构师、后端、前端、测试、产品经理 5 个 |
| 架构师 Agent | 讨论的固定入口与终止者，决定是否结束本轮（`done`）及下一个发言者 |
| 轮次（Round） | 用户发一条需求 → 多个 Agent 依次发言 → 直到架构师 `done` 的一次完整讨论 |
| Turn | 单个 Agent 的一次发言（含工具调用 + 结构化收尾） |
| 会话（Session） | 一次"会议"，承载多轮讨论 + 最终会议纪要，对应 DB 一行 |
| RAG | 检索增强生成：pgvector 向量 kNN + pg_trgm 关键字召回 + 本地 cross-encoder rerank |
| MCP | Model Context Protocol，外部工具服务协议（如百度 AI Search） |
| HITL | Human-in-the-Loop，人工介入审批 Agent 的高风险动作 |
| Checkpoint | 图执行的中间状态快照，用于中断后恢复 |
| 动态工作流 | 架构师在多种预置编排模板中按需求类型动态选择的路由策略 |

## 2. 产品背景

### 2.1 现状与问题

MeetMind 当前是一个 TypeScript monorepo（`apps/runtime` 后端 + `apps/desktop` 前端）实现的多 Agent 协作 Demo：5 个角色 Agent 围绕用户需求自由讨论，架构师作为入口和终止者；每个 Agent 拥有独立 PostgreSQL 表 + 私有 RAG 工具；用户可结束会议并获得会议纪要与各角色待办。

但它目前停留在"单机单用户、聊天可用"的阶段，距离一个可对外、可运维的产品还有显著差距：

- **没有用户体系**：无注册/登录、无权限、所有会话全局共享，无法多人使用。
- **没有工具治理**：Agent 可调用文件读取、进程查看等工具，但无权限策略、无风险分级、无沙箱、无人工审批，存在安全隐患。
- **容错薄弱**：进行中的讨论一旦中断（关闭会话/进程退出）即丢失，无 checkpoint / 恢复 / 重发能力。
- **编排单一**：只有"架构师 + 各 Agent 自主选下一个"一种路由模式，缺少面向不同需求类型的固定工作流。
- **运维不友好**：模型 URL / Key / 名称 / 温度等只能改 `.env` 重启，无法在前端配置。
- **能力有缺口**：会话标题需手动改、无 todolist、RAG 无 query 改写、不支持文件作为消息输入、无上下文用量与压缩策略。

### 2.2 产品定位

> MeetMind 是一个**以用户为主导、多 Agent 协同分析需求并产出可执行结论**的智能会议协作平台。

用户提出需求 → 架构师 Agent 接入并组织讨论 → 多角色 Agent 借助私有知识库、工具与外部检索反复讨论 → 用户随时结束会议，获得**会议纪要**与**每个角色的后续工作清单**。

### 2.3 产品价值

- **对用户**：把"开一次跨职能需求评审会"压缩成一次对话，几分钟内得到结构化结论 + 分工待办。
- **对团队**：每个 Agent 绑定本职知识库与工具，输出贴合角色、可直接落地。
- **对平台**：可扩展的工具 / 工作流 / 知识库体系，使其能从需求评审扩展到更多协作场景。

## 3. 产品目标与成功指标

### 3.1 业务目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 支持多用户安全使用 | 完成注册/登录/匿名/权限/会话隔离，可对外开放 |
| G2 | Agent 高风险动作可控可审计 | 工具具备权限策略 + 风险分级 + 沙箱 + HITL 审批，0 起未授权高危操作 |
| G3 | 讨论过程具备容错与可恢复性 | 中断后可从 checkpoint 恢复，恢复成功率 ≥ 99% |
| G4 | 编排可按需求类型自适应 | 提供 ≥ 3 种固定工作流，架构师可动态选择 |
| G5 | 运行时可在前端自助配置 | 模型 URL/Key/名称/温度/think 模式、模型切换均可在前端完成，无需重启 |

### 3.2 关键成功指标（北极星 & 辅助指标）

| 指标 | 定义 | 目标（首个 GA 后 3 个月） |
|---|---|---|
| 北极星：有效会议数 | 产出有效会议纪要的会话数 / 周 | 持续增长 |
| 会议完成率 | 结束并成功生成纪要的会话 / 创建的会话 | ≥ 70% |
| 首轮自动命名准确率 | 自动标题被用户保留（未手动改）的比例 | ≥ 80% |
| 工具审批合规率 | 高危工具调用经 HITL 审批后执行的比例 | 100% |
| 恢复成功率 | 中断会话成功恢复的比例 | ≥ 99% |
| 平均轮次时长 | 单轮讨论端到端耗时 | 在可接受区间并随上下文压缩下降 |

## 4. 用户画像与使用场景

### 4.1 用户画像

| 画像 | 描述 | 核心诉求 |
|---|---|---|
| 匿名体验者 | 不注册，快速试用 | 零门槛体验完整讨论 + 纪要 |
| 个人注册用户 | 注册后长期使用 | 会话持久化、跨设备一致、个人记忆沉淀 |
| 团队管理员 | 管理团队成员与权限 | 用户权限分级、用量与审计 |
| 平台运维 | 配置模型与工具 | 前端配置 runtime、工具风险策略管理 |

### 4.2 核心使用场景

1. **需求评审**（主场景）：PM 抛出一个产品需求，5 个 Agent 从架构、前后端、测试、产品角度讨论，产出方案与分工。
2. **技术方案讨论**：架构师主导，针对一个技术问题组织多角色评估。
3. **快速问答**：用户只是简单提问，架构师一句话回答并结束（已支持的"反喧宾夺主 / 一句话结束"逻辑）。
4. **带资料的讨论**：用户上传 PRD/设计稿/文档（md/pdf/word/txt），Agent 基于文件内容讨论（待实现）。

## 5. 现状基线（已实现能力）

> 本节是研发的事实依据，新需求一律在此基线之上做增量，不重复造轮子。

### 5.1 已实现功能清单

| 模块 | 已实现能力 | 关键实现位置 |
|---|---|---|
| 多 Agent 编排 | 5 角色 Agent + LangGraph 条件边路由；架构师固定入口；`routeToWhichAgent` 兜底防卡死 | `graph/builder.ts`、`graph/route.ts`、`graph/state.ts` |
| Agent 推理 | 两阶段 invoke（Phase 1 工具循环 + Phase 2 结构化收尾）；结构化输出 `{content, next_agent, done}` | `agents/base.ts` |

| 本地模型 | 本地 embedding（all-MiniLM-L6-v2，384 维）+ 本地 rerank（bge-reranker-base），纯 ONNX 无 torch | `database/models/embedding.ts`、`reranker.ts` |
| 工具体系 | LangChain `tool()` 单例 + `ToolRegister`；现有工具：`rag_search` / `web_fetch` / `read_file` / `list_dir` / `list_processes` / `echo`；MCP 工具异步登记（百度 AI Search） | `tools/*Tool.ts`、`tools/toolRegister.ts`、`tools/mcp/mcpClient.ts` |
| 会话持久化 | `sessions` / `messages` 两张表；会话增删改查、消息按 `(session_id, seq)` 落库；会话"已结束"状态持久化 | `database/chat/chatStore.ts` |
| 实时通信 | 单条 SSE firehose（按 sessionId 路由）+ JSON-RPC；流式 delta、工具调用、轮次事件 | `server/sseServer.ts`、`server/rpcServer.ts`、`server/httpServer.ts` |
| 讨论控制 | 开始讨论（`chat.send`）/ 打断（`chat.interrupt`，AbortController）/ 结束并整理纪要（`chat.end`） | `server/rpcServer.ts`、`server/runDiscussion.ts` |
| 会议纪要 | 一次 LLM 调用产出 `minutes` + 各角色工作段；失败降级占位 | `agents/base.ts: summarizeAll`、`server/meetingSummary.ts` |
| 前端聊天 | 聊天窗口、流式气泡、工具调用展示、思考中占位、会议结束弹窗、会话列表/搜索、**手动重命名**、删除 | `apps/desktop/src/components/*`、`stores/*` |
| 前端主题 | 浅/深主题切换（含气泡配色随主题切换）；空会话占位提示 | `App.vue`、`stores/ui.ts`、`theme/agentColors.ts` |

### 5.2 现有约束与既定设计（不在本期修改）

- LLM 走 OpenAI 兼容协议（默认小米 MiMo），`modelKwargs.thinking.type = "disabled"` 不可移除。
- PostgreSQL（pgvector）是硬依赖，启动 `pingDb()` 失败即 `process.exit(1)`。
- 运行用 tsx，改后端代码（尤其新增 RPC method）后必须重启 runtime。
- 命名习惯（`snake_case` 的 state 字段、`this.RAGRetriever` 等）为有意为之，需求实现时遵循。

### M1 · 用户与账户体系

**模块背景**：当前所有会话全局共享、无任何用户概念（`chatStore` 注释明确"单用户 demo，鉴权以后再加 user_id"）。要对外开放，必须建立账户、权限与数据隔离。

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M1-01 | 用户注册 | P0 | 提供注册页面；支持邮箱/用户名 + 密码注册；密码加盐哈希存储；基本校验（唯一性、强度） | 新用户可注册成功并落库；重复账号被拒；密码非明文存储 |
| FR-M1-02 | 用户登录 | P0 | 提供登录页面；签发会话凭证（JWT/Session）；登录态在前端持久化与刷新续期 | 正确凭证可登录并保持登录态；错误凭证被拒；登出可清除登录态 |
| FR-M1-03 | 匿名使用 | P0 | 保留当前"无需登录即可使用"的体验；**匿名会话的数据保存在本地 better-sqlite3**（不进服务端 PostgreSQL），与注册用户的云端数据物理隔离；可引导登录后将本地匿名数据导入到账户 | 未登录用户仍可完整体验讨论 + 纪要；匿名数据落本地 better-sqlite3、与注册用户数据隔离；登录后可选导入 |
| FR-M1-04 | 用户权限等级 | P0 | 定义角色与权限分级（如 匿名 / 普通用户 / 管理员）；不同等级对应不同工具调用、模型配置、用量上限 | 越权操作被后端拒绝并返回明确错误；权限可由管理员调整 |
| FR-M1-05 | 用户级会话持久化隔离 | P0 | `sessions` / `messages` 增加 `user_id`；所有会话读写按当前用户过滤；提供数据迁移脚本兼容旧的无 user 数据 | 用户只能看到/操作自己的会话；跨用户访问被拒；旧数据平滑迁移 |
| FR-M1-06 | 用户级记忆管理 | P1 | 为每个用户维护跨会话的长期记忆（偏好、历史结论摘要等），并在新会话中可选注入；提供记忆的查看/编辑/清除 | 记忆按 user 隔离；可被检索注入；用户可管理自己的记忆 |

**关键交互流程（注册→登录→隔离）**
1. 访客打开应用 → 可直接匿名使用，或进入注册/登录页。
2. 登录后 → 拉取该用户的会话列表（按 `user_id` 过滤）。
3. 所有 `chat.*` / `session.*` RPC 携带登录态 → 后端校验身份与权限 → 按 `user_id` 读写。

**依赖**：需在 `chatStore` 表结构、`rpcServer` 鉴权中间件、前端路由（登录/注册页）三处协同改造。

### M2 · 会话管理增强

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M2-01 | 首轮主题自动命名 | P1 | 会话开始首轮讨论后，自动总结本轮主题并更新 session title（替代目前仅手动重命名）；用户手动改过则不再自动覆盖 | 首轮结束后标题自动更新为贴合主题的短语；用户手动改名后自动命名不再触发 |
| FR-M2-02 | 会话列表分组 | P2 | 会话列表支持分组（按时间/自定义分组/收藏等其一或组合）；分组可折叠 | 会话可被归入分组并正确展示；分组状态持久化 |

**FR-M2-01 设计要点**：在首轮 `round_done` 后触发一次轻量 LLM 调用（或复用纪要逻辑）生成 ≤ N 字标题；新增标志位区分"系统自动命名"与"用户手动命名"，避免自动逻辑覆盖用户意图。

### M3 · 编排与工作流

**模块背景**：当前只有一种编排——架构师入口 + 各 Agent 自主选 `next_agent`（即"自主路由"）。需要在此之上增加一组**预置工作流模板**，由架构师在入口处按需求类型动态选择，使讨论方式与需求复杂度匹配。

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M3-01 | 动态工作流选择 | P1 | 架构师在入口处识别需求类型，从下方「工作流模板库」中动态选择一条工作流来组织本轮讨论；无明确匹配时回落到现有"自主路由" | 架构师能识别需求类型并选对工作流；各工作流的执行特征符合其模板定义；自主路由作为兜底始终可用 |
| FR-M3-02 | 工作流模板：ReAct | P1 | 推理-行动循环：Agent 交替"思考→调用工具→观察结果→再思考"，直到给出结论。**现有各 Agent 的 Phase 1 工具循环本质即 ReAct**，本需求是将其显式化为可选工作流 | 选择 ReAct 时讨论以"边推理边调工具"方式推进，工具结果实时回灌 |
| FR-M3-03 | 工作流模板：Plan-and-Execute | P1 | 计划-执行：架构师先产出完整计划（步骤 + 每步负责角色），再按计划逐步派发给对应 Agent 执行；执行偏差时可回看/修订计划 | 选择该流时先输出可见计划，再按计划顺序路由执行；计划可被展示与追踪 |
| FR-M3-04 | 工作流模板：Reflection | P1 | 反思迭代：Agent 产出初稿后，由反思环节（架构师或评审角色）批判并要求修订，迭代 N 轮或达到质量阈值后收敛（即 Reflexion / Evaluator-Optimizer 思路） | 选择该流时存在"产出→批判→修订"的可见迭代；迭代有上限防止死循环 |
| FR-M3-05 | 单角色快速模式：CoT | P2 | 思维链快速作答：面向闲聊/简单问答，单 Agent（通常架构师）做链式推理后一句话结束，不做多角色路由（CoT 本质是推理/提示模式，非多角色编排，故归为"快速模式"） | 简单输入走 CoT 时由单角色逐步推理后直接 `done`，不无意义路由其他角色 |
| FR-M3-06 | TodoList 功能 | P1 | 讨论过程中沉淀结构化待办（可由 Agent 产出、用户编辑）；会话内可查看/勾选；与会议纪要的"各角色工作项"打通 | 待办项可被创建、展示、勾选完成、持久化；与纪要工作段一致 |

**工作流模板库一览**

| 模板 | 定位 | 适用需求类型 | 备注 |
|---|---|---|---|
| 自主路由（现状） | 多角色自由讨论，各自选下一个 | 开放式需求评审 | 默认兜底，始终可用 |
| ReAct | 推理-行动循环 | 需要反复查资料/调工具 | 已是各 Agent 内部机制，显式化为流 |
| Plan-and-Execute | 先计划后执行 | 步骤明确的复杂任务 | 计划可见、可追踪 |
| Reflection | 产出-批判-修订迭代 | 对质量要求高、需打磨 | 含 Evaluator-Optimizer 双角色变体 |
| CoT（快速模式） | 单角色链式推理 | 闲聊/简单问答 | 非多角色编排，单角色一句话结束 |

> **关于 "Harness"**：业界没有名为 "Harness" 的标准工作流模式；通常指 "agentic harness（智能体外壳/编排骨架）"，即把上述模式编排、调度起来的外层框架本身——在本系统中对应 FR-M3-01 的"动态选择 + 路由"机制，而非一种独立工作流。详见 11.3 已澄清项。
>
> 其他可按需扩展的主流模式：Router（路由分发）、Orchestrator-Workers（编排者-执行者）、Multi-Agent Debate（多智能体辩论）。本期先落地上表 4 条核心模板。

**设计要点**：将"工作流模板"抽象为路由策略（进入/退出条件 + 节点推进规则），架构师在第一跳输出中除 `next_agent` 外额外选择 `workflow`；`routeToWhichAgent` 按所选工作流推进，无匹配时回落到现有自主路由（延续现有兜底设计，保证图永不卡死）。

### M5 · 工具治理与安全（P0）

**模块背景**：现有工具中已含 `read_file` / `list_dir` / `list_processes` 等可触达本机资源的能力，但无任何权限/风险/沙箱/审批控制。多用户开放前必须补齐。

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M5-01 | 工具调用权限策略（Policy） | P0 | 为每个工具定义可调用主体（按用户权限等级 / 按 Agent 角色）；后端在工具执行前做策略校验 | 无权限的工具调用被拦截并返回明确原因；策略可配置 |
| FR-M5-02 | 工具风险等级 | P0 | 为每个工具标注三档风险等级 **low / medium / high**；风险等级驱动后续沙箱与审批策略（见下方分级表） | 每个工具有明确风险等级（low/medium/high）；等级元数据可被策略与 UI 读取 |
| FR-M5-03 | 高风险操作沙箱 | P0 | Agent 执行修改文件、运行命令等高风险操作时，必须在受限沙箱环境中执行（隔离文件系统/网络/资源） | 高风险操作在沙箱内执行，无法越界访问宿主敏感资源 |
| FR-M5-04 | Human-in-the-Loop 审批 | P0 | 高风险工具调用前暂停，向用户推送审批请求；用户允许后才执行，拒绝则跳过并告知 Agent | 高风险调用必经用户审批；审批结果驱动执行/跳过；超时有默认策略 |

**工具风险分级表（low / medium / high）**

| 风险等级 | 定义 | 现有工具示例 | 沙箱（FR-M5-03） | HITL 审批（FR-M5-04） |
|---|---|---|---|---|
| **low** | 只读、无副作用的检索/查询 | `rag_search`、`web_fetch`、`web_search`、`echo` | 不需要 | 不需要 |
| **medium** | 读取本机/环境信息，可能涉及敏感数据 | `read_file`、`list_dir`、`list_processes` | 受限只读沙箱 | 可配置（默认提示，可设为需审批） |
| **high** | 有副作用：改文件、写入、执行命令、对外发起变更 | （现暂无，未来如 write_file / run_command 等） | **强制沙箱** | **强制人工审批** |

> 风险等级是工具的元数据，策略（FR-M5-01）按"用户权限等级 × 工具风险等级"共同决定是否放行。

**HITL 交互流程**
1. Agent 在 Phase 1 请求调用高风险工具 → 命中风险等级阈值。
2. 后端暂停工具执行 → 经 SSE 推送审批卡片（工具名 + 入参 + 风险说明）到前端。
3. 用户「允许 / 拒绝」→ RPC 回传决策 → 后端在沙箱中执行或跳过 → 结果接回工具循环。

**依赖**：与 M6（暂停/恢复需要 checkpoint 支撑）、SSE/RPC 事件协议扩展强相关。

### M6 · 容错与状态管理（P0）

**模块背景**：当前讨论状态只在内存，`busy` + `AbortController` 仅用于打断；进程退出或会话关闭即丢失进行中的轮次。需要引入 checkpoint。

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M6-01 | Checkpoint 保存与恢复 | P0 | 在 Agent 回答中关闭会话/进程退出/被打断等特殊情况下保存图执行 checkpoint；重启或重开会话后可从断点恢复（建议接入 LangGraph checkpointer + Postgres 持久化） | 中断后能从最近 checkpoint 恢复讨论，不丢已完成 turn；恢复成功率 ≥ 99% |
| FR-M6-02 | 恢复期事件队列 | P0 | Agent 恢复过程中若用户再次输入，输入进入事件队列有序处理，不与恢复中的执行冲突 | 恢复中用户的新输入被正确排队、不丢失、不乱序、不并发踩踏 |
| FR-M6-03 | 消息回退重发（Resume） | P1 | 支持"切换到上一次发出消息前"的状态并重新发送消息（回退到某 checkpoint 重新走分支） | 用户可回退到上一条消息前并重发；重发基于正确的历史快照 |

**FR-M6-01 设计要点**：评估 LangGraph 的 checkpointer 机制，以 `session_id`（+ thread）为键将 checkpoint 落 PostgreSQL；与现有 `messages` 落库解耦但可对账。

|---|---|---|---|---|

### M8 · 模型与运行时配置

**模块背景**：当前模型 URL/Key/名称/温度等只能改 `.env`（`settings.ts` 读 `process.env`）并重启 runtime。需支持前端自助配置。

| 编号 | 需求 | 优先级 | 描述与功能点 | 验收标准 |
|---|---|---|---|---|
| FR-M8-01 | 设置入口（聊天窗口左下角设置图标） | P1 | 在**聊天窗口左下角**放一个设置图标，点击打开模型管理面板：可**新增 / 删除**多个模型配置，每个配置含 `BASE_URL` / `API_KEY` / `MODEL_NAME` / `temperature` / `thinking` 开关 | 点击图标打开面板；可增删模型配置并持久化；敏感项（API_KEY）安全存储 + 脱敏展示 |
| FR-M8-02 | thinking 开关 | P1 | 每个模型配置带一个 `thinking` 开关，决定**是否开启该模型的思考（thinking）功能**：开 → 允许模型思考；关 → 关闭思考（即当前后端默认行为 `thinking.type="disabled"`） | 开关状态正确透传到模型调用的 `modelKwargs.thinking`；切换后对后续讨论生效 |
| FR-M8-03 | 前端配置即时生效 | P1 | 在前端保存的模型配置无需手改 `.env`、无需重启 runtime 即可对后续讨论生效 | 保存后下一轮讨论即使用新配置 |
| FR-M8-04 | 输入框模型切换 | P1 | 在消息输入框右下角提供模型快速切换选择器，复用 FR-M8-01 配置的模型列表 | 用户可在发送前选择本轮使用的模型；选择被正确应用到该轮讨论 |

**设计要点**
- `getSettings()` 当前是单例缓存且 `apiKey/baseUrl/modelName/temperature` 直接读 `process.env`；前端动态配置需引入"运行时可变配置层"（按用户/会话覆盖 env 默认值），并安全管理密钥（加密存储 + 脱敏）。
- **⚠️ 与现有约束的冲突点**：`agents/base.ts` 目前硬编码 `modelKwargs: { thinking: { type: "disabled" } }`，且 `CLAUDE.md` 将其列为"不能改"。FR-M8-02 要求让 thinking 可由用户开关 → 实现时需**把该字段从硬编码改为读运行时配置**，这与现有约束直接冲突，须先由项目负责人确认是否解除该约束（已记入 11.3 与风险表）。

## 10. 风险与依赖

| 风险/依赖 | 说明 | 应对 |
|---|---|---|
| 沙箱实现复杂度 | 高风险工具沙箱涉及文件系统/进程隔离，工程量大 | R1 先覆盖最高危工具（改文件/执行命令），其余按风险等级渐进接入 |
| Checkpoint 与现有落库一致性 | checkpointer 与 `messages` 双写可能不一致 | 明确以 checkpoint 为恢复源、messages 为展示源，提供对账 |
| OpenAI 兼容后端差异 | 结构化输出/流式在不同后端表现不一（现有代码已多处兼容） | 延续两阶段 + coerce 兼容策略，前端配置模型时给出兼容性提示 |
| thinking 开关 vs 既有约束 | `base.ts` 硬编码 `thinking.type="disabled"` 且 CLAUDE.md 标注"不能改"，FR-M8-02 要求其可由用户开关 | 需项目负责人确认解除该硬编码约束，改为读运行时配置；解除前 FR-M8-02 不可落地 |
| 密钥安全 | 前端配置 API_KEY 带来密钥泄露风险 | 后端加密存储 + 前端脱敏 + 按用户隔离 |
| 多 Agent 并发与事件队列 | 恢复期再输入易引发并发踩踏 | 以 session 为粒度串行 + 事件队列（延续现有 `busy` 单飞设计） |

## 11. 附录

### 11.1 当前技术栈速览

- **Monorepo**：`apps/runtime`（tsx 运行的 TS 后端）+ `apps/desktop`（Vue3 + Pinia + Vite，Tauri 外壳）

### 11.3 已澄清结论（Resolved）

1. **匿名数据存储**：匿名用户数据保存在**本地 better-sqlite3**，与服务端 PostgreSQL 物理隔离；可引导登录后导入到账户。（落 FR-M1-03、数据模型表）
2. **工具风险等级**：三档 **low / medium / high**，分级表见 M5。（落 FR-M5-02）
3. **工作流模板**：采用主流编排模式落地——核心 3 条 **ReAct / Plan-and-Execute / Reflection** + 单角色快速模式 **CoT** + 现有"自主路由"兜底；架构师动态选择。"Harness" 非标准工作流，对应编排骨架本身，不单列。（落 FR-M3-01 ~ FR-M3-06）
4. **设置入口与 thinking**：聊天窗口**左下角设置图标** → 模型管理面板，可增删模型配置（apikey / url / 模型名 / 温度 / thinking）；**thinking 开关决定是否开启模型思考功能**。（落 FR-M8-01 ~ FR-M8-04）
5. **上下文统计口径**：**只统计模型上下文（token）用量，不计费、不统计费用**。（落 FR-M7-01）
